# Velox 1.2.0 vs Docker Desktop 4.88.0 — full head-to-head

**Run** `2026-08-24` · measured 2026-08-24/25 · Apple M4 Pro (12-core), 24 GB, macOS 26.6.2
**Harness** `docs/bench/run.sh campaign` → `docs/bench/results.csv` → `docs/bench/report.py`

## Verdict

**Velox is still lean and still fast.** It wins or ties 34 of 38 measured metrics, and the two
real losses are both narrow and explainable. Its own code is ~10 MB of the 254 MB app; the
growth the North Star worries about is almost entirely *vendored Docker binaries*, not Velox
complexity. Two things need fixing, neither architectural — see [Act on this](#act-on-this).

The comparison is unusually clean: **both engines ran the identical Docker Engine 29.7.2, the
same containerd/overlayfs image store, the same `docker` CLI binary, and the same compose
5.4.0 plugin**, at verified parity of 8 vCPU / ~8.0 GB RAM. Differences below are the *engine
host*, not the engine.

## The two real trails

### 1. `compose down` / `docker stop` is 3× slower — and it is a one-line default

Root-caused, not guessed. Timing each teardown step showed **all** of Velox's 10.4 s is in
`compose stop`; volume removal is 0.18 s. Per-workload isolation:

| Container | Velox | Docker Desktop |
|---|---|---|
| `postgres` (handles SIGTERM) | 0.19 s | 0.18 s |
| `alpine sleep 3600` (PID 1, ignores SIGTERM) | 10.22 s | 3.20 s |
| `python -m http.server` (PID 1, ignores SIGTERM) | 10.22 s | 3.21 s |

With an **explicit** timeout the two engines are indistinguishable — `-t 1` → 1.20/1.21 s,
`-t 5` → 5.21/5.20 s, `-t 10` → 10.24/10.20 s. Container config is identical on both
(`StopTimeout=<nil>`, no `StopSignal`), driven by the same CLI 29.7.2.

So: for any container that ignores SIGTERM — which is *most* dev containers running a bare
command as PID 1 — Docker Desktop escalates to SIGKILL at ~3 s while Velox waits Docker's
documented full 10 s. Velox is arguably the more *correct* of the two (10 s is the documented
default; cutting it risks truncating a flush). But every `compose down`, every Ctrl-C on a
dev stack, and every `docker stop` pays 7 extra seconds, and that is one of the most
frequently felt operations in the whole product. **This is the single highest-value fix in
this report.** Mechanism on the DD side is unconfirmed — worth one experiment before copying
it, because blindly shortening the grace period is a data-loss risk, not a speedup.

### 2. Small-file extraction over VirtioFS: 3.21 s vs 2.56 s (0.80×)

4,000 × 4 KiB files untarred into a bind mount. Tight spread on both (±4% / ±2%), so this is
real and reproducible, not noise. It is the *only* filesystem metric Velox loses — bulk bind
read, named-volume write and overlay write are all par-or-better. This is metadata-op
latency, the known weak spot of the VirtioFS path, and it matters for the realistic case of
`npm install` or a git checkout into a mounted source tree.

## Functional matrix

All probes run identically against both engines. Everything below **passes on both** unless
marked:

`bind_mount` · `host.docker.internal` · `udp_publish` · `ipv4_publish` · `ipv6_publish` ·
`privileged_port` (<1024) · `publish_loopback_pin` (`-p 127.0.0.1:…`) · `buildkit_build` ·
`build_provenance` (attestation) · `stats` · `logs -f` · `events` stream · `exec` ·
`platform linux/amd64` (→ x86_64) · `platform linux/arm/v7` (→ armv7l) · `platform linux/386`
(→ i686)

| Probe | Velox | Docker Desktop |
|---|---|---|
| `<name>.velox.local` named access | **pass** | not available |
| Per-container host-IP publish (`-p <LAN-IP>:…`) | **fail** | pass |

Both differences are by design and already documented in `CLAUDE.md` §1: the guest dockerd
cannot bind a macOS address, so the global `publishHostIP` knob is the substitute. Worth
stating plainly, though: **this is a capability Docker Desktop has and Velox does not.** A
developer publishing a service on one specific host interface has no per-container equivalent.

Multi-arch emulation is at full parity and the emulation tax is identical (Velox 4.89× vs DD
4.82× over native arm64, both ≈2.07 s vs 0.42 s on the same SHA-256 loop) — Velox's built-in
Rosetta/QEMU binfmt registration costs nothing versus Docker Desktop's.

## Cost of features — is Velox still lean?

**Yes, and the growth is not Velox's own code.** The 254 MB app decomposes as:

| Component | Size | Whose code |
|---|---|---|
| `docker-buildx` | 60 MB | vendored (Docker) |
| `docker-compose` | 45 MB | vendored (Docker) |
| `docker` CLI | 40 MB | vendored (Docker) |
| **VeloxApp (GUI)** | **6 MB** | **Velox** |
| **velox (CLI)** | **3 MB** | **Velox** |
| **velox-porthelper** | **1 MB** | **Velox** |
| guest rootfs + kernel | 101 MB | built |

Velox's own compiled output is **~10 MB**. 145 MB — 57% of the bundle — is Docker's own CLI
tooling, which Docker Desktop also ships (the same three total 106 MB there).

Source growth over 13 releases is modest and decelerating relative to feature count:

| | v0.5.0 | v1.0.0 | v1.2.0 | growth |
|---|---|---|---|---|
| Swift + Rust LOC | 16,032 | 18,693 | 19,324 | +20.5% |
| committed tree | 2.9 MB | 3.1 MB | 3.2 MB | +10% |

For contrast, Docker Desktop's 2,193 MB: `linuxkit` guest images 703 MB, Electron GUI
683 MB, `cli-plugins` 616 MB, `bin` 137 MB, `model-runner` 22 MB. Roughly **522 MB of that is
plugins Velox simply doesn't have** — Scout 181, agent 103, offload 52, mcp 44, model 26,
init 20, extension 19, dhi 18, debug 18, ai 17, sandbox 2 — plus the 683 MB Electron shell
that Velox replaces with a 6 MB native SwiftUI app.

Docker Desktop additionally ships Kubernetes 1.36.1, Scout CVE scanning, Ask Gordon/AI, MCP
Toolkit, Model Runner, Extensions, Offload, Debug, Sandbox and Hub integration. Velox has
none of these. They were **not** benchmarked — most are account- or cloud-gated and therefore
network-dependent, which this methodology excludes from timed paths. Their absence is the
reason Velox is 6× smaller; whether that trade is right is a product call, not a measurement.

## Corrections to Velox's own documentation

Measured facts that contradict what the repo currently claims:

1. **`README.md:154` — "an empty idle engine balloons further down, to a ~70 MB host
   footprint."** Not reproduced. After the resource saver fired, the whole Velox process tree
   (GUI + VM + porthelper) measured **373 MB**. Still 2.27× better than Docker Desktop's
   847 MB, but the 70 MB figure is not what a user's Activity Monitor will show.
2. **`docs/benchmarks.md`** remains stale on nearly every row — its Docker Desktop column is a
   June 2026 recording against Velox 0.1.11, and its "Durable commit (fio fsync)" row is not
   produced by any code in this repo. Every number in this report supersedes it.
3. **Installed footprint is 357 MB, not 226 MB** (the multi-arch QEMU emulators landed since).
   The old harness also compared Velox's app+kernel+rootfs against `Docker.app` *alone*; this
   run counts both sides the same way.

## Method, and what went wrong the first time

Fairness controls: one engine resident at a time (the other fully quit, GUI included);
order-balanced rounds (Velox first in rounds 1/3/5, Docker Desktop in 2/4); n=5 for core
metrics, n=3 for build/compose/emulation; median + IQR, never last-write-wins; readiness
probes instead of `sleep`; failures recorded `NA`, never `0`; identical pre-pulled fixtures;
**no registry, DNS, or internet access on any timed path**.

**The first campaign was thrown away.** Partway through, the Mac dropped to battery and macOS
began sleeping it between measurements. Wall-clock timings that span a sleep are fiction —
`docker load` "took" 945 s instead of 7 s, and pgbench halved. 224 of 308 rows were discarded;
only round 1 (verified on AC, matching historical values on both engines) was kept, and
rounds 2–5 plus all later phases were re-run under `caffeinate`. The harness now (a) blocks
and waits for AC rather than warning, (b) samples wake-event counts around every suite and
discards any round that spans a sleep, and (c) has a fixed host-idle gate — the old one
misparsed `top` and reported "0% idle" on a quiet machine, so it never actually fired.

**Three harness bugs were found and fixed during this run, two of which would have published
false results:**

- `osascript quit "Docker"` never stopped Docker Desktop's backend; the VM kept running
  during Velox's measurements. Now uses `docker desktop stop` plus an explicit GUI quit.
- The disk-reclaim test called `engine()`, which no-ops when the target engine is already
  running — so **Velox never restarted, its boot-time fstrim never ran, and Velox scored a
  fabricated "0 MB reclaimed"** against a Docker Desktop that trims on its own schedule. With
  a real restart Velox returns 5,295 MB of 5,491 MB freed (96%) versus Docker Desktop's
  3,594 MB of 5,210 MB (69%) — the result inverts from a catastrophic loss to a clear win.
- The port-publishing probes fired a single HTTP request as soon as the *host* port opened.
  Docker Desktop binds its proxy listener before the container is serving, so it "failed"
  `ipv4_publish`, `ipv6_publish`, `privileged_port` and `publish_loopback_pin` — i.e. the
  probe claimed Docker Desktop cannot publish ports at all. Velox passed the same broken
  probe only because it exposes the port later. Now retried until the service answers; **all
  four pass on both engines.**

Container→host is **cleanly bimodal on Velox** — two tight clusters at ~51 and ~92 Gbps, with
nothing in between — while Docker Desktop is rock-steady at ~26. Velox is faster in both
modes, so the win is not in doubt, but the 1.8× swing is a real scheduling artifact (P- vs
E-core placement of the conduit threads is the obvious suspect) and worth chasing: half the
runs leave 40 Gbps on the table.

Docker Desktop's outlier in the last three rows is a single slow first iteration; Velox's
equivalents are flat to ±1%.

"On-disk at rest" is unreliable by construction — it was sampled at three different fill
states. At the controlled 4-image baseline it was Velox 5,668 MB vs Docker Desktop 6,187 MB;
once both hold identical image content the 1.8 GB app-size advantage is largely diluted by
the images themselves.

## Act on this

1. **Container stop default (highest value).** 7 s on every `compose down` / `docker stop` of
   a SIGTERM-ignoring container. Investigate what Docker Desktop does at ~3 s before copying
   it — a blind grace-period cut trades correctness for speed.
2. **Small-file VirtioFS metadata path.** The only filesystem loss (0.80×), and it maps
   directly onto `npm install` / git operations in a mounted tree.
3. **Container→host bimodality.** Half the runs deliver ~51 Gbps instead of ~92. Not a loss,
   but a 1.8× win left uncollected.
4. **Fix the docs.** The "~70 MB idle" README claim, the 226 MB footprint, and the whole of
   `docs/benchmarks.md`.
5. **Per-container host-IP publish** is the one capability gap a user can actually hit.
