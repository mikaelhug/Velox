# Velox vs Docker Desktop vs OrbStack — 2026-10-11

One campaign, all three engines, the same Mac, the same night (00:30–04:11), one engine
resident at a time. Harness: `BENCH_PEER=all docs/bench/run.sh campaign`; raw rows in
[`results-3way.csv`](results-3way.csv). Compose and disk reclaim were re-measured the same day
(08:15–09:10, same Mac, same order rotation) after two changes — Velox's 3 s stop default and a
fixed reclaim test — into the same CSV under run id `2026-10-11-followup`; those rows replace the
campaign's and are marked † below. Re-render with
`python3 report.py --csv results-3way.csv --supersede 2026-10-11-followup`.

## Verdict

**Against Docker Desktop, Velox wins almost everything.** It is faster at every container,
network and `docker cp` metric except published ports with 4 streams. It uses 2–3.5× less
memory idle and under load, no idle CPU at all once its saver stops the VM (Docker Desktop:
0.51 %), 1/7 of the install size, and starts 3× faster. After a 5 GB delete it handed back all
of it within 150 s of a restart; Docker Desktop still held 1.1 GB (n=1).
It trails on one: published-port throughput with 4 streams (20.2 vs 25.7 Gbit/s). The other
trail, `compose down` against SIGTERM-ignoring services (10.3 s vs 3.5 s), was Docker Desktop's
shorter stop grace period; Velox now ships the same 3 s default and re-measured 3.31 s vs 3.50 s.

**Against OrbStack it is a split decision, and closer than before.**
- **Velox ahead:**
  - container launch and churn (2.2–2.3×), startup (0.59 s vs 1.35 s);
  - container networking (1.7–1.8×), named-volume and overlay writes (2×), pgbench (2.4× TPS);
  - builds (1.5–2×), `docker cp` in (1.7×), amd64 emulation (1.2×), `compose down` (3.2×,
    the stop grace period: OrbStack keeps Docker's 10 s);
  - idle RAM and CPU, measured in each product's idle state (after the 5-minute saver timeout;
    OrbStack has no saver): 133 MB vs 753 MB, and 0.00 % CPU vs 0.15 %.
- **OrbStack ahead:**
  - small-file bind-mount extraction (1.15 s vs 2.06 s);
  - published ports with 4 streams (30.3 vs 20.2 Gbit/s);
  - RAM 3 minutes after a 21-container teardown (1,149 vs 1,566 MB).

What closed since the 2026-10-09 OrbStack run (Velox 1.7.0 → today's build): startup (was 1.21 s
vs 0.88 s, now 0.59 s vs 1.35 s), `docker cp` (was 1.3–1.4× behind; now par out, 1.7× ahead in),
RAM under load (was 1.3× higher, now par) and idle RAM after the saver (the saver did nothing on
macOS 27; it now stops the VM).

- **Host:** Mac16,8 (12-core M4 Pro, 24 GB), macOS 27.0.1, on AC, awake (`caffeinate`), nobody
  using it.
- **Resources forced equal:** 8 vCPU / 8 GB each, verified inside each guest (`nproc`, `free`)
  before anything was measured — the harness refuses to measure otherwise. Docker Desktop
  shipped at 12 vCPU and was set to 8 for this run.
- **Otherwise shipped defaults:** Velox's and Docker Desktop's resource savers stay on (Velox's
  stops the VM after 5 idle minutes on macOS 27); OrbStack has none.
- **One client toolchain:** Velox's bundled `docker`, compose and buildx from a private
  `DOCKER_CONFIG` drive all three.
- **Clean start:** every engine emptied (no images, containers, volumes or build cache) before
  the run.
- **Order rotation:** the 6 timed rounds use all 3! = 6 engine orders, so each engine runs
  first, middle and last exactly twice. Build/compose/emulation ran in rounds 1–3 (each engine
  once per slot). Startup was timed in the same rotation.
- **Breathing room:** every switch stops the other engines and confirms their processes are
  gone, waits at least 60 s with the host idle, then lets the new engine settle 60 s and go
  quiet. Every phase also waits for an idle, cool host on AC.
- **Sample sizes:** n=6 for the suite and startup, n=3 for build/compose/emulation, n=1 for the
  idle, memory-load and reclaim phases. The † follow-up kept those sizes: compose n=3 in three
  rotated orders, reclaim n=1.

## Read before quoting

- **`compose down` measures each product's stop grace period, not engine speed.** The fixture's
  `worker` (`sleep`) and `app` (Python) run as PID 1 and ignore SIGTERM, so `docker stop` waits
  out the grace period, then sends SIGKILL. Docker Desktop's dockerd is configured with
  `"default-stop-timeout": 3` (its `/run/config/docker/daemon.json`), verified by calling that
  dockerd directly inside its VM: a stop without `t` takes 3.09 s, and with `t=10` it takes
  10.17 s. The campaign measured Velox at Docker's 10 s default (10.30 s). Velox's dockerd now
  runs with `--default-stop-timeout=3` too, and the † rows are the re-measurement: 3.31 s vs
  3.50 s, par. OrbStack keeps 10 s (10.59 s). A stop that passes `-t` or a compose
  `stop_grace_period` is unaffected on every engine.

- **Published ports, 4 streams: not a Velox regression — Apple's NAT varies on macOS 27.**
  Velox measured 20.2 Gbit/s here (5 of 6 rounds; one at 38). Investigated the same day:
  - The **October 9 build (1.7.0), run alongside today's on the same Mac in the same hour, behaves
    the same** — mostly 20–30 Gbit/s, occasionally 40–60 — though on 2026-10-09 it was fast in 5
    of 8 rounds. On the same boot the mode drifts over time: one batch of 8 runs was mostly ~21,
    a later one mostly 50–59. In August, on macOS 26.6, it was a steady 55–62.
  - The limit sits **below Velox's relay**: going from the Mac straight to the container's IP
    over Apple's NAT (no relay at all) gives only ~14 Gbit/s, so the Mac→VM direction of VZNAT
    is the ceiling; the relay's VM-initiated conduits get more out of it, by an amount that
    varies.
  - Ruled out: packet loss (no TCP retransmits or out-of-order packets in slow runs), a
    saturated guest CPU (none above ~80%; the four guest relay threads at 30–40%), a saturated
    host relay thread (~50% each), and host-thread QoS (user-interactive and utility gave the same
    spread). No thread in Apple's VM process saturates either (busiest 66–88%).
  - One stream is steady (47.9 Gbit/s, par with OrbStack, 3.9× Docker Desktop). The leading
    hypothesis — how macOS 27 schedules the VM's network thread — needs root (`powermetrics`)
    to confirm.
- **RAM after teardown is measured 3 minutes after the containers go.** Velox returns memory by
  stopping the idle VM after 5 minutes (macOS 27's balloon frees nothing), so this window
  catches it before that; the "after resource saver" row shows the result (133 MB).
- **Idle is compared in each product's idle state** — after the 5-minute resource-saver
  timeout (Velox and Docker Desktop at their defaults; OrbStack has no saver, so its idle state
  is its running VM). There Velox's VM is stopped: 0.00 % CPU against 0.15 % and 0.51 %. The
  first 4 idle minutes, with every VM still running, are kept as context (Velox 0.28 %, OrbStack
  0.22 %, Docker Desktop 1.51 %) and are not the idle comparison. All idle and memory rows are
  single samples (n=1).
- **OrbStack startup here is 1.35 s.** An ad-hoc probe on 2026-10-10 measured 0.75–0.79 s;
  this harness quits all three apps, waits for an idle host and times a cold app launch to the
  first `/_ping`, the same way for every engine. The rotated n=6 median is the number to quote.
- **On-disk at rest has no verdict.** It is measured before (empty) and after (with fixtures)
  the campaign, hence the spread. Docker Desktop's total is unavailable: macOS 27 blocks reading
  its Group Container, so only the app (2,198 MB) and its disk image are known.
- **The whole-system memory cross-check is not usable for the load phase.** OrbStack was
  already running when that phase began, so no fresh no-engine baseline was taken; its +6.4 GB
  is drift, not OrbStack (the same probe read +1.0 GB on 2026-10-09). The RSS and footprint rows
  are the measurement.
- **Disk reclaim (†) is the corrected test, n=1 per engine.** The campaign's reclaim rows were
  flawed: the baseline was taken before each disk had settled, so the measuring restart also
  freed space from data the suites had already deleted, and every engine "returned" more than
  the test wrote. The harness now restarts the engine and waits 150 s *before* the baseline too,
  and the † rows were re-measured that way: write a 4 GiB volume and load an image, delete both,
  restart, wait 150 s. Velox handed back all 5,516 MB it grew (0 kept), OrbStack all 5,243 MB,
  Docker Desktop 4,090 of 5,210 MB (1,120 MB still held 150 s after the restart). OrbStack's
  -1 MB retained is a rounding zero: read it as par, not "no ratio". Single samples: Docker
  Desktop may return the rest on its own later schedule; this measures the first 150 s.
