Velox vs alternatives

Same Mac, same resource caps, same pinned images, one engine under load at a time. The harness and full methodology live in the repo.

Recorded run · 11 October 2026

Apple M4 Pro, macOS 27.0.1, 8 vCPU / 8 GB each

Velox 1.7.1 against Docker Desktop 4.94.0 and OrbStack 2.2.3, in one campaign: the same Mac, the same night, one engine resident at a time, each at a verified 8 vCPU / 8 GB, all three emptied first and driven by the same docker CLI and compose plugin. Six rounds ran the engines in all six orders, so each went first, middle and last twice. Medians, n=6 (n=3 for builds and compose, n=1 for the memory phases). A verdict needs at least 15% and non-overlapping spreads; anything closer is on par. Rows marked † were re-measured the same morning in the same rotation, after Velox adopted a 3 s stop default and the disk-reclaim test was fixed.

All three passed every functional probe: bind mounts, host.docker.internal, TCP, UDP and IPv6 publishing, per-container host IPs, privileged ports, BuildKit with attestations, and linux/amd64, linux/arm/v7 and linux/386 emulation. Velox and OrbStack add direct <name>.local container access. Velox returns memory by stopping the idle engine after 5 minutes, because macOS 27's memory balloon frees nothing, so the 3-minute post-teardown row catches it before that. The 4-stream published-port result swings between 20 and 60 Gbit/s on macOS 27 for every Velox build tested, 1.7.0 included. The Mac-to-VM direction of Apple's NAT measures about 14 Gbit/s with no Velox code in the path; on macOS 26.6 it was a steady 60. compose down measures the stop grace period for containers that ignore SIGTERM: Velox and Docker Desktop ship 3 s, OrbStack keeps Docker's 10 s. Disk reclaim is a single sample per engine, taken 150 s after a restart.
